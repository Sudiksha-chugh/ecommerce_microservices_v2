# Version-controlled consumer contracts

HTTP consumer expectations live in `http/v1.ts`. Provider verification calls real Express app routing, authentication, serialization and error handling, with stubbed business dependencies. These tests do not prove database behavior; the isolated regression and live suite supply that evidence. Auth, Catalog, Cart, Orders, Payments and Inventory read responses plus administrative authorization are covered. Search response/auth checks currently live in `tests/contracts/http.test.ts`.

`events/v1.json` pins all current payload schemas independently of future provider changes. The schemas represent **wire input**, preserving UUID constraints before normalization transforms. `tests/contracts/events.test.ts` compares current providers with this baseline and invokes the actual envelope validator for version, producer, enum, unknown-field and payload rejection. Zod refinements such as cross-field linkage and positive-money refinements cannot all be expressed in generated JSON Schema; runtime validator tests remain essential.

Ownership follows `packages/messaging/src/topology.ts` queue bindings and each service's handler. No new registry service or Pact broker is introduced. Consumers own expectations; providers own implementations. Changes require reviewing consumer parsing behavior, security requirements and version support. Never regenerate this baseline automatically as part of a check. Deliberate breaking changes require a new version and coordinated consumer migration.

Compatibility is directional: provider output must fit consumer expectations. Required fields, types, enum expansion, strict unknown-field behavior, authentication, status, method, path and version metadata are checked. Optional HTTP fields are tolerated where consumers allow them; existing event payloads reject unknown fields. Unsupported JSON Schema keywords are conservatively compared for equality. This is a bounded checker for this repository's schema subset, not a general proof of backward compatibility. Notification service consumes business events; it does not produce an invented notification event family.

## Phase 22 mutation expectations

`http/mutations-v1.ts` defines 18 consumer-owned contracts for the actual Catalog, Cart, Orders/Checkout, Inventory and Payments/Refund mutation routes. Provider verification invokes the real Express app factories and middleware with controlled business dependencies. It verifies request rejection, response shapes, state values, authentication, admin authorization, required idempotency headers and unchanged identity forwarding. Database/provider deduplication is verified independently by the live matrix and isolated integration tests; a stable stub response alone is not claimed as that evidence.

`mutationCompatibility` evaluates response/error compatibility in the provider-to-consumer direction and request acceptance in the opposite direction. It detects authentication, identity semantics, response-body kind, accepted HTTP status set and registry version changes. Registry version 1 is a consumer expectation revision, not an invented versioned HTTP URL or header. Operations using a stable resource identity (confirmation/release/payment/refund reconciliation) are distinguished from principal-key creation and operations without a declared idempotency protocol. Cart additive operations are not falsely declared idempotent.

Intentional incompatible fixtures cover missing required fields, changed types, absent authentication, unsupported states, identity semantics changes, incompatible errors and newly required request fields. Event contracts and their strict unknown-field policies remain unchanged.
