# ADR 009: Transactional Outbox and Inbox for Reliable Events

Status: Accepted for Phase 11

Direct PostgreSQL + RabbitMQ writes cannot commit atomically: an order can commit without publication, or publication can succeed while the database result is lost. Orders now inserts the order, its items, and one durable order.created.v1 event using the same transaction client. The event is built from persisted rows, not request prices. Its outbox UUID is its logical eventId; producer, original occurredAt, payload, correlationId, and causationId are stored in a complete JSONB envelope with matching metadata constraints. Unique order/type/version and the existing owner/idempotency key preserve one order and one logical event on replay. Legacy orders are not backfilled or republished.

A shared event-persistence package accepts each owner's PostgreSQL pool, the existing RabbitMQ publisher, logger, clock for timings, and retry policy. Tables remain service-owned: Orders gets outbox_events; Inventory and Payments get inbox_events. Shared SQL templates are version-controlled starting points copied into each owner's explicit checksum-tracked migrations; there is no automatic schema synchronization or shared database. Orders adds a local aggregate foreign key, so outbox rows cannot be orphaned and an audited order cannot be deleted without explicit outbox retention decisions. Existing development business data is not changed by these additive migrations.

An independently runnable Orders outbox process claims a bounded batch in a short transaction using FOR UPDATE SKIP LOCKED. It commits UUID claim tokens, worker identity, database-clock leases, and attempt counters before any network call. Eligible expired leases can be reclaimed. Success/failure/release updates compare the token and PROCESSING state. Leases alone cannot prevent an old worker from publishing; fencing protects database state, while inbox uniqueness protects committed effects against duplicate publication.

Workers reconstruct and validate the original envelope, require RabbitMQ publisher confirmation, then mark PUBLISHED. A confirmation means broker acceptance, not consumer success. A crash or database failure after confirmation can leave PROCESSING, or an uncertain database update may already have succeeded. Recovery reads durable state: pending/expired rows may publish again with the same identity. Broker failures retain rows and schedule database-backed retry. Default retry ceilings are 5s, 30s, 120s, 300s, 900s, with optional bounded jitter/scaling; maximum attempts defaults to six including the initial claim. Invalid contracts, mandatory unroutable events, and known permanent broker configuration errors go directly to NEEDS_ATTENTION. Exhausted transient retries and crash leases do likewise. Nothing is silently deleted. Requeue is operator-invoked, only from review state, validates the saved contract, resets the finite retry budget, retains lifetime attempt counts and identity, and increments an audit requeue count.

Workers publish bounded batches in parallel without holding database locks over I/O. Shutdown stops claims and waits for bounded active work; unstarted claims are released by token, and uncertain in-flight work is recovered through expiry. Worker modules are explicit entry points, never imported by app factories or tests. Process readiness is verified before startup. The broker can be absent without blocking order creation or losing committed events. The RabbitMQ manager supplies bounded confirms, reconnect/backoff, mandatory returns, and manual acknowledgments.

Inbox deduplication uses PRIMARY KEY (consumer_name,event_id), because different logical consumers can legitimately handle one event in the same service database. The processor inserts the inbox row and executes a supplied local database effect on the same transaction client. Concurrent INSERT ON CONFLICT waits for the first transaction: after commit, the duplicate verifies the normalized full-event fingerprint and skips effects; after rollback, a waiting transaction can process it. Reusing an eventId with changed contents is a permanent handler failure. Handler/write failures roll back inbox and effects; an ambiguous COMMIT is retried safely because either neither committed or the durable receipt suppresses repetition. The RabbitMQ handler returns only after COMMIT, so the messaging framework ACKs afterwards. Crash after COMMIT and before ACK redelivers, then skips effects.

Inventory and Payments use explicit INBOX_ENABLED opt-in, require messaging enabled, and reject diagnostic-consumer bypass. Their Phase 11 order.created handlers commit receipt-only inbox records using logical names inventory.order-created.receipt.v1 / payments.order-created.receipt.v1. They never reserve stock, create payment intents, charge customers, or update orders. Isolated test handlers use dedicated test_effects tables to prove transactional atomicity. Future business handlers must use distinct logical consumer identities; receipt-only processing must not silently stand in for checkout work.

The event factory creates a new child event UUID, retains the parent's correlationId, and sets causationId to the parent eventId. Outbox and RabbitMQ retries never regenerate identity or time. Public HTTP APIs do not accept arbitrary event publication or trusted prices. Existing JWT, database role isolation, RabbitMQ topic credentials, test vhost, and queue isolation remain in force. Metadata logging includes IDs, claim token, worker, attempts, latency, outcomes and safe enum failure classifications, without payloads or credentials. Durable outbox statistics expose counts, failures, expired leases and oldest pending age; inbox process counters/logs expose duplicates and failures.

There is no exactly-once network delivery claim. Exactly one committed local database effect per immutable event/consumer is supported while inbox records are retained and all effects use the provided transaction. External HTTP/provider operations cannot be made atomic by this inbox and must not run inside its callback; later orchestration uses durable state and provider idempotency. Handlers should honor cancellation and use bounded SQL operations. Receipt/outbox retention and operator access require explicit policies; no automatic cleanup destroys audit/deduplication state. Active checked-out PostgreSQL clients handle connection errors explicitly and are discarded; the processor/worker avoids an unhandled Client error terminating the service. Integration tests scope migration locks by scratch schema and bound pool/file concurrency; production public-schema locking is preserved. Database outages may exhaust RabbitMQ's finite consumer retry budget into DLQ, requiring manual replay after recovery. Workers require external process supervision. Checkout Saga remains Phase 12.

Tests use restricted test databases, random schemas and RabbitMQ namespaces. They kill real processes before order COMMIT, after order COMMIT, after provider publication confirmation, before inbox COMMIT, and after inbox COMMIT/before ACK; surviving workers/processors recover the same logical event and one committed test effect. Deferred commit errors, stale fencing, concurrent duplicate delivery, broker retry and outage behavior are covered separately.
