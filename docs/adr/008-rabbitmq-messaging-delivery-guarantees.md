# ADR 008: RabbitMQ Messaging and Delivery Guarantees

Status: Accepted for Phase 10

RabbitMQ provides topic routing, durable queues, publisher confirms, manual consumer acknowledgments, and broker-driven delayed retry. A shared `@ecommerce/messaging` workspace owns connection recovery, validation, topology, publishing, consuming, retry classification, structured logging, and bounded shutdown. Domain services retain their HTTP and database ownership.

Events use a strict versioned envelope: eventId identifies the logical event and never changes during retry/redelivery; correlationId groups a workflow; causationId identifies the preceding event/command or is null. Eight independent v1 payload schemas use UUIDs, ISO timestamps, integer paise, enum reasons, and no provider secrets or unnecessary personal data. `eventType=order.created`, `eventVersion=1` routes as `order.created.v1`. Unsupported types/versions, invalid producer/payload, and malformed JSON are poison messages. Payload schemas do not depend on internal database row types.

A durable topic exchange `commerce.events` has four explicitly bound service queues. Queues, retry queues, and DLQs are durable quorum queues. Each owner has a separate durable direct handoff exchange. Retry queues have TTLs of 5s, 30s, and 120s and dead-letter back to the original queue through that owner's handoff exchange. Quorum retries use at-least-once dead-lettering with reject-publish overflow; queue length is capped at 10000. The local broker is a single node and does not provide multi-node availability. Nonlocal deployment needs TLS, replicated quorum membership, secret management, monitoring, and capacity planning.

Publishing validates and serializes before using a confirm channel with persistent delivery and mandatory routing. Each wire publication has a separate private tracking UUID, while messageId stays the logical eventId. Returns precede publisher confirms and cause an unroutable error; negative confirms, timeout, and channel/connection loss fail outstanding calls. A bounded pending-confirm map (100 by default) and fail-fast unavailable behavior prevent an unbounded application buffer. A confirmed publish proves broker acceptance, not successful consumer processing. A lost confirmation can leave publication uncertain; a caller must retain the same eventId when retrying. There is no exactly-once delivery claim.

Consumers parse JSON, validate envelope/version/payload and queue routing, then invoke a handler with retry metadata and an abort signal. Manual ACK occurs only after successful work on the current channel generation. Default per-consumer prefetch is 5. Handler deadlines default to 30 seconds and abort context on timeout; connection loss also releases managed work. Stale handlers cannot ACK a new channel; a handler must honor cancellation or use durable fencing/idempotency for its own side effects in later phases.

Temporary handler failures use confirmed republishing to the next retry queue, carrying unchanged body/eventId/correlationId and bounded numeric retry count. Malformed events, unsupported versions, invalid retry metadata, permanent handler failures, and exhausted retries hand off to the DLQ. Failure metadata contains only enum classifications and source queue, never arbitrary error strings or payload logs. The original is ACKed only after handoff confirmation. If the handoff is uncertain or unroutable, close the connection with the original unacknowledged and recover with capped, jittered exponential backoff. No immediate nack/requeue loop is used. A confirmed handoff followed by loss before ACK can duplicate deliveries; inbox deduplication is required in Phase 11. Headers are bounded metadata, not a security boundary against an authorized malicious publisher; inbox/outbox must preserve logical identity.

Connection and channel closure invalidates the generation, aborts handler context, fails pending publications, and reconnects with delay. Recovery redeclares topology, recreates confirm/consumer channels, and registers each consumer once. A readiness barrier prevents handling deliveries until setup completes. Startup broker failure is recoverable and publication fails fast. Shutdown cancels consumers, waits for bounded work, aborts unfinished handlers, and closes the connection so unacknowledged messages are redelivered.

Orders, Inventory, and Payments bootstrap messaging only with explicit `MESSAGING_ENABLED=true`. Existing health remains liveness; `/ready` reports disabled/ready/reconnecting. No business publisher is called from an HTTP transaction or reconciliation worker. Optional diagnostic consumers have no repository/client access. The demo runs in a unique test namespace; manual replay processes one operator-selected DLQ message, validates it, preserves logical identity, resets the finite retry budget, and ACKs the DLQ copy only after confirm. Invalid contracts remain quarantined; changing an event's meaning requires a new eventId with causation linking the original.

Local infrastructure uses a named persistent volume, localhost AMQP/management ports, non-guest credentials from ignored environment files, separate service users and explicit resource/topic permissions. Services cannot read/configure another owner's queues or publish unrelated event families. A separate test vhost and restricted namespace-only test user isolate integration tests. No broker endpoint is exposed through Gateway. Local environment files are a development convenience; production should mount credentials from a secret store rather than commit them or embed them in images.

Transactional outbox/inbox is deferred to Phase 11. Publishing after a database commit without an outbox would create an unsafe dual write, so Phase 10 deliberately declares infrastructure and exposes testable adapters only. Actual checkout orchestration belongs to Phase 12.
