# ADR 007: Durable payment attempts, provider idempotency, and reconciliation

Status: Accepted for Phase 9

Payments owns `payments_db` and a restricted role. It has no cross-service database access or foreign keys. Admin-authenticated intent creation supplies trusted order/user IDs and a positive safe-integer amount in INR; customers cannot choose arbitrary checkout totals. Later checkout integration must derive these values from Orders. Existing Orders, Cart, and Inventory behavior remains unchanged.

Payments persist the authorized creator separately from the customer owner. Intent keys are scoped to the creator through `(created_by,idempotency_key)` uniqueness and a SHA-256 fingerprint of the normalized complete request. `(user_id,idempotency_key)` and unique order IDs provide additional model constraints. Replaying the same creator/key returns the original payment's current state; conflicting bodies or order/owner-key collisions return 409. One order has one payment in this phase.

The state machine permits CREATED → PROCESSING; PROCESSING → SUCCEEDED, FAILED, or REQUIRES_RECONCILIATION; and REQUIRES_RECONCILIATION → SUCCEEDED or FAILED. Reconciliation that remains unknown leaves its state unchanged. SUCCEEDED and FAILED are terminal. Repeated processing or reconciliation of terminal payments returns their current result without another charge. Processing an uncertain/in-flight payment does not create another attempt. Reconciling an unprocessed intent returns 409.

Each processing claim takes a row lock, creates attempt 1 with a stable provider request ID equal to the payment UUID, sets a random lease token and database-clock deadline, and commits. The provider HTTP call happens after that transaction releases all locks. The result is persisted in a new transaction that locks the payment, checks its lease token and allowed state transition, and atomically updates payment and attempt. A stale response cannot overwrite a reclaimed lease or a terminal result. A failure to commit the attempt prevents calling the provider. A failure to save a provider result leaves the durable attempt recoverable.

The deterministic mock provider is a separate HTTP process on localhost port 4006, with its own `mock_provider_db`, role, and autocommitted charge/idempotency table. It has no access to Payments' database. Its unique request ID and stored amount/currency prevent repeated charge requests from creating a second charge, including concurrent requests and provider restart. Result scenarios are explicitly configured on the provider process, never accepted in payment request bodies: success, decline, delayed timeout, temporary definitive failure, successful charge with lost response, and unresolved ambiguity. Scenario changes affect new operations; existing records remain authoritative. It is local simulation infrastructure, not a production provider or public deployment endpoint.

Database transactions cannot atomically commit an external provider charge. A timeout/disconnection/invalid provider response does not establish that no charge occurred. Payments therefore records UNKNOWN on the attempt and REQUIRES_RECONCILIATION on the payment. It preserves the original request ID and never substitutes a fresh charging key. Explicit declines/known temporary failures are definitive FAILED and are not automatically retried in this single-attempt model.

Reconciliation queries the original operation; it never charges. It uses the same database-backed lease protocol, with expired PROCESSING leases moved to REQUIRES_RECONCILIATION. Final provider results become terminal; missing/pending provider operations remain uncertain. Not-found is deliberately not proof of failure because an original network operation might still commit. Such cases require a later definitive provider result or operator policy; no automatic new charging is attempted. A bounded periodic worker selects due candidates and calls the same reconciliation operation. Concurrent workers recheck each candidate under its row lock and skip active leases. No in-memory lock is required for correctness. A persisted next-reconciliation time bounds retries. Shutdown stops scheduling, awaits worker/network work, drains HTTP, and closes the pool under a deadline.

This provides effectively-once charging when the provider durably honors idempotency, not exactly-once network delivery. Integration tests use two distinct restricted test databases and random schemas, kill a real Payments child process after a provider commit and before local result persistence, restart it, and confirm reconciliation and another process restart preserve a single charge. Tests also inject a local commit-stage failure and prove the provider's committed result survives rollback.

Every Payments endpoint verifies RS256 JWT signature, issuer, audience, expiry, and subject independently. Intent/process/reconcile require admin role until secure internal identities arrive. Customers can read only their own records; other/nonexistent records return 404. Both customer and admin JSON omit provider IDs, leases, fingerprints, failure internals, and credentials. Logs use generic failure messages or counts. No real payment gateway, refunds, saga, messaging, outbox, or notification service is introduced.
