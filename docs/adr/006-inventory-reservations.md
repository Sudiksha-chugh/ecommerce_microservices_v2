# ADR 006: Inventory ownership and transactional reservations

Status: Accepted for Phase 8

Catalog describes products. Inventory tracks scarce, mutable quantities with concurrency and deadline rules, so it owns a separate `inventory_db`, restricted PostgreSQL role, migrations, and independently runnable Express process. Inventory checks product existence through Catalog HTTP when stock is set. There are no cross-database foreign keys or direct Catalog/Orders database reads. Orders and Cart retain their existing behavior.

Use raw SQL and pg, consistent with previous phases. `inventory` holds unconsumed total stock and reserved stock, with database constraints ensuring both are non-negative and reserved never exceeds total. Available stock is calculated as their difference in the same SELECT. PUT sets absolute unconsumed stock and its conditional UPSERT refuses a total below active reservations.

Reservations hold stock without consuming it while an operation is pending. A confirmation consumes held units by decrementing total and reserved together, keeping available stock unchanged. Release or expiration decrements only reserved. The ledger allows only RESERVED, CONFIRMED, RELEASED, and EXPIRED. The repository explicitly permits only transitions from RESERVED; repeating the same confirm/release is a stable read of persisted state. Incompatible terminal transitions return 409.

A unique order/product pair cannot detect replay with a different product set. Add `inventory_reservation_requests`, whose order UUID is the durable serialization point and whose fingerprint hashes a versioned, sorted, normalized list of all products and quantities. Creation of this parent, stock changes, and reservation rows commit in one transaction. Identical concurrent/reordered requests return one logical group with unchanged reservation IDs and deadline. Changed quantities or added, removed, or replaced products return 409. Terminal replays return current persisted status without reviving stock or extending TTL. Failed initial transactions leave no fingerprint.

Use READ COMMITTED transactions with explicit row locks. All reservation mutations first lock parent order rows, then stock rows in deterministic ascending product UUID order. Availability is checked for every product before any writes. Unique constraints, row locks, and stock constraints protect against overselling even across service instances. Workers claim multiple parents in order and then lock the global union of affected products in order. Operations never acquire a parent after a stock lock. PUT locks only its stock row. This lock protocol avoids cycles for supported operations; bounded statement/connection deadlines still return sanitized failures under excessive contention.

Store deadlines in PostgreSQL, using one database-clock deadline for an entire group after availability locks. Replays do not reset it. Confirmation/release checks the PostgreSQL clock again after acquiring stock locks, with one materialized decision for the group. If due, it commits EXPIRED and releases quantities, then rejects the attempted transition with 409. A confirmation waiting on a lock therefore cannot consume an already expired group.

The worker timer only schedules scans; persisted deadlines define expiration. Each batch selects due parent groups with `FOR UPDATE SKIP LOCKED`, reloads their state, locks affected stock rows, and atomically changes RESERVED to EXPIRED and releases stock. Parent locks serialize workers, confirmation, release, and replays. Multiple workers may claim different groups without double release. Database rollback covers partial failures. Expiration is eventually reflected in public stock reads at the next scan; reads do not mutate data. Polling/batch limits trade simplicity for bounded cleanup latency. Worker logs use counts and generic failures, and graceful shutdown stops scheduling and awaits active work before pool closure.

All writes verify RS256 JWTs independently using only Auth’s public key and require admin role. Existing JWT claims do not support secure internal service identities, so arbitrary service headers and customer JWTs never grant access. Internal service authorization belongs to later checkout integration. No payments, checkout saga, messaging, outbox, or Orders orchestration is included.

References: [PostgreSQL explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) and [SELECT locking clauses / SKIP LOCKED](https://www.postgresql.org/docs/17/sql-select.html).
