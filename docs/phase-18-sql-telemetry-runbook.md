## Enable and observe

Both `OTEL_ENABLED=true` and `OTEL_SQL_ENABLED=true` are needed. Defaults remain disabled. Existing PostgreSQL wrappers cover Auth, Catalog, Orders, Inventory, Payments, Notifications, Search and the mock payment provider. Promise and callback query APIs retain their result/error identities and argument order. Transaction clients remain wrapped through `connect`; release/rollback and messaging behavior are preserved. Custom streaming/submittable query extensions are outside the observed query API contract; services use ordinary Promise/callback queries.

Settings in `.env.observability.example`:

- `OTEL_SQL_SAMPLE_RATIO`: 0–1, default 0.1; applies to fingerprints only.
- `OTEL_SQL_MAX_FINGERPRINTS`: 1–32, default 32, per process.
- `OTEL_SQL_RETENTION_MS`: 1,000–3,600,000, default 300,000. Expired entries are removed on observation/report access; expiry uses monotonic process time, with no background timer or growing persistence file. `lastSeen` is a process-relative monotonic timestamp, not an epoch timestamp.
- `OTEL_SQL_SLOW_MS`: 1–10,000, default 250. Completion duration includes driver/pool waiting from query invocation through settlement, rather than database-only execution time.

Invalid SQL tuning disables the feature without breaking a business startup. No per-query network request, storage write or EXPLAIN is performed by the wrapper. Export uses the existing bounded asynchronous SDK pipeline. Query input is inspected only for sampled fingerprint creation, capped at 8,192 characters. A lexical reduction removes string/dollar/numeric/boolean/null literals, bind numbers, quoted identifiers and comments before constructing a SHA-256 digest (96 displayed bits). Unsupported or malformed input is omitted. Only the opaque digest survives; normalized text, SQL and parameter arrays are never retained. Fingerprints group shapes, are not reversible query text, and are not PostgreSQL query IDs or proof of equivalent execution plans. Digest collisions and grouping differences are possible; no correctness decision uses a fingerprint.

The in-memory report contains at most 32 fingerprints with sampled counts, errors, slow counts, sum/max duration and fixed histogram buckets. Sampling is not extrapolated into exact per-fingerprint totals. Admission drops and cumulative observations are reported explicitly; overflow does not evict and churn entries until expiry. Storage is bounded per process and disappears on restart. No database telemetry table, raw-query cache or diagnostic log is created.

All-execution metrics are `sql.query.executions`, `sql.query.errors`, `sql.query.slow` and `sql.query.duration` (seconds). Their only application label is the bounded SQL operation category; service identity comes from the existing resource. Fingerprints are deliberately absent from metric labels. Sampled dependency spans may contain only `db.query.fingerprint`. Existing SDK views cap each instrument at 128 attribute sets; SDK queues, export deadlines and shutdown bounds remain in force. Prometheus retention remains 24 hours / 256 MB in the opt-in disposable stack. No raw SQL, parameters, plan expressions or credentials enter logs, span attributes or metric labels.

## Internal reporting and authentication

When explicitly enabled, each PostgreSQL-backed business service exposes `GET /internal/sql` through its existing cryptographic JWT verifier and admin-role check. Responses set `Cache-Control: no-store`; missing/invalid/expired/wrong-audience or wrong-issuer tokens are rejected, and customers receive 403. Gateway forwarding does not expose these internal routes. The mock provider receives SQL metrics but has no new reporting HTTP surface. Service reports describe that process only, not a merged cluster-wide store; Grafana provides service-level aggregate metrics.

Business service instances do not receive diagnostic credentials or create diagnostic pools. Their `/internal/sql/queries` list is empty and `/internal/sql/explain` is disabled. Run the separate internal diagnostic process only when needed:

```
SQL_DIAGNOSTICS_ENABLED=true npm run sql:diagnostics
```

Set `SQL_DIAGNOSTIC_SERVICE` to one of `catalog`, `auth`, `orders`, `inventory`, `payments`, `notifications`, `search`; set the database host/port/name, `SQL_DIAGNOSTIC_PGUSER`, `SQL_DIAGNOSTIC_PASSWORD_FILE`, `JWT_PUBLIC_KEY_FILE`, `JWT_ISSUER`, `JWT_AUDIENCE`. Passwords come from a private file, never an argument or committed env file. The diagnostic listener binds only `127.0.0.1`, default port 3218. Database targets are limited to loopback addresses; use an independently authenticated local tunnel to an approved read-only replica rather than sending database credentials across an unprotected network. An isolated diagnostic process targets one service/database. It does not proxy targets supplied by clients. Limit exposure at the host/network layer as well as using admin authentication.

`GET /internal/sql/queries` lists approved diagnostic IDs. An admin may POST exactly `{"queryId":"catalog.product-by-id"}` to `/internal/sql/explain`. No SQL, bind values, relation names, options or query-string parameters are accepted. JSON is limited to 1 KB and parser errors use fixed responses. Unknown/cross-service IDs are rejected before connecting. No JWT, raw exception message or input body is logged. Missing configuration or failed authentication fails closed.

## Database boundary and approved queries

Provision the diagnostic role and replica permissions through an independently reviewed operator process. The diagnostic system never creates or alters roles, schemas, queries, indexes or statistics. It targets PostgreSQL 17, including its MAINTAIN privilege checks and generic JSON plans. Never point it at a development database to make tests pass.

A role must be named `sql_diag_<lowercase-name>`, LOGIN, NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION and NOBYPASSRLS, with no role memberships or owned application objects. It must have CONNECT and schema USAGE, SELECT on exactly the source-reviewed public table, no table-level or column-level write privileges, grant options, MAINTAIN, sequence access or read access outside the approved table, no database CREATE/TEMP, and no CREATE on application schemas. [PostgreSQL privilege inquiry functions](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE) check both table and column grants; PUBLIC grants count toward effective privileges and must already satisfy this boundary. Prefer an operator-provisioned replica; do not revoke shared production PUBLIC grants opportunistically to enable diagnostics. Use a role-level `default_transaction_read_only=on` as an additional deployment guard. Tests establish this configuration only inside a new owned disposable PostgreSQL instance.

The versioned source registry contains seven lookup templates: Catalog products, Auth users, Orders orders, Inventory inventory, Payments payments, Notifications notifications and Search search_projection_state. Each selects only its identifier with a typed generic UUID predicate. These are explicitly approved representative lookup diagnostics, not automatically reconstructed application queries or plans for every observed fingerprint. Registry expansion requires code/security review; requests cannot register queries. Ordinary table/partition kind is required and row-level-security targets are rejected. Trusted schema ownership is a prerequisite: read-only mode alone does not make arbitrary SELECT/functions, policies, views or planner-time evaluation safe. Do not use this tool against untrusted schemas/extensions.

Before every plan request, the tool begins READ ONLY, sets transaction-local statement timeout 1,000 ms, lock timeout 100 ms, idle transaction timeout 2,000 ms and search path `pg_catalog`, then verifies effective role/ownership/table privileges. The separate pool has max one connection, 1,000 ms connect timeout, 1,500 ms client query timeout and short idle lifetime. Admission is one concurrent request by default (library hard maximum two), no queue, and ten admitted attempts per minute. Busy requests return 429. Every path attempts ROLLBACK; a connection with failed rollback is destroyed.

The only planner statement is `EXPLAIN (FORMAT JSON, GENERIC_PLAN TRUE, VERBOSE FALSE, COSTS TRUE, SETTINGS FALSE)` plus a source-approved SELECT. No `EXPLAIN ANALYZE`, runtime parameter values, autonomous analysis, DDL or automatic tuning exists. Generic plans may differ from custom value-dependent plans and do not measure actual rows, execution duration, disk spills or buffer traffic. PostgreSQL cost units are estimates, not milliseconds. [PostgreSQL 17 EXPLAIN documentation](https://www.postgresql.org/docs/17/sql-explain.html) describes these distinctions; [read-only transaction restrictions](https://www.postgresql.org/docs/17/sql-set-transaction.html) provide an additional boundary rather than SQL validation.

## Deterministic analysis and dashboard

The analyzer emits at most 128 nodes with depth at most 32. Only numeric nonnegative bounded estimates, allowlisted node types, numeric parent links and fixed finding codes survive. Relations, indexes, aliases, output columns, conditions, sort keys, expressions and settings are discarded. Unknown node names become `Other`. It identifies sequential scans, joins, high estimated-cost sorts, and conservative filter/sort/join index-review opportunities. Thresholds are explicit (cost 1,000, sequential scan estimated output rows 1,000). A sequential scan may be optimal; estimates do not prove a missing index. Findings request human review and include no executable SQL or automatic changes.

`commerce-sql-performance` is the eighth provisioned dashboard in the existing opt-in Phase 17 stack. It charts operation/service execution rates, p95 latency, error rates and slow-query rates. Existing credentials, datasources and retention apply. The successful live gate retrieved all four SQL metric families from the actual Collector→Prometheus path and executed all 19 provisioned dashboard queries. The proof deliberately creates one fixture-only SQL error and one 300 ms sleep to establish positive error/slow observations. All existing checkout, charge, inventory, retry/DLQ and four telemetry-backend outage assertions remain required.
